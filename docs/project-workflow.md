# 범용 해커톤 프로젝트 진행 순서

이 순서는 데이터 분석, 머신러닝, 최적화, 웹·앱 시제품이 포함된 다양한 해커톤을 위한 기본 흐름입니다. 공식 일정과 제출 규정에 맞춰 단계를 합치거나 순서를 조정하세요.

## 1. 규정과 미션 확인

**할 일:** 공식 문제 설명, 평가 기준, 제출물, 마감, AI·외부 코드·데이터 사용 규칙을 확인합니다.

**남길 것:** `templates/mission-brief.md`에 원문 링크, 핵심 요구, 확인되지 않은 규정을 적습니다.

**완료 기준:** 팀원 모두가 해결할 사용자 문제와 제출 형태를 한 문장으로 설명할 수 있습니다. 불확실한 규정은 가정으로 숨기지 않고 질문으로 남깁니다.

## 2. 문제를 측정 가능한 목표로 바꾸기

**할 일:** 사용자, 현재 불편, 제안할 해결 방식, 성공 지표를 정합니다. 예: 오류율 감소, 탐색 시간 단축, 예측 오차 감소, 처리량 증가.

**남길 것:** 미션 브리프와 `templates/analysis-plan.md`의 질문, 결과 변수, 기준선, 성공 기준.

**완료 기준:** 어떤 결과가 좋아진 것인지 측정할 방법이 있고, 최소기능제품(MVP)에 포함할 것과 제외할 것이 정해져 있습니다.

## 3. 데이터와 자료의 인벤토리 작성

**할 일:** 파일·API·수집 경로별 출처, 권한, 라이선스, 관측 단위, 기간, 스키마, 민감정보 가능성을 파악합니다. 원본은 보존합니다.

**남길 것:** `templates/source-log.csv`, `templates/data-dictionary.md`; 출처가 불명확하면 확인 항목으로 기록합니다.

**완료 기준:** 각 파일이 어디서 왔고 무엇을 한 행으로 나타내는지 설명할 수 있으며, 사용·공개 가능 여부가 구분돼 있습니다.

## 4. 데이터 품질과 분석 가능성 점검

**할 일:** 행·열 수, 자료형, 결측, 중복, 범위, 단위, 범주 표현, 시점, 그룹, 라벨 분포를 점검합니다. 문제를 고칠 때 원본을 덮어쓰지 않고 재현 가능한 변환을 만듭니다.

**남길 것:** [데이터 검증 프롬프트](../prompts/04-dataset-validation.md)로 만든 점검 보고서와 처리 결정.

**완료 기준:** 치명적인 오류와 보정 불가능한 제한을 식별했고, 각 처리 규칙의 근거가 남아 있습니다. 검사 결과가 모두 정상이어야만 통과하는 것은 아닙니다. 제한을 공개하고 목표에 쓸 수 있는지 판단합니다.

## 5. 간단한 기준선부터 만들기

**할 일:** 규칙 기반, 다수 클래스 예측, 평균·중앙값, 단순 검색, 기본 휴리스틱처럼 설명하기 쉬운 방법을 먼저 구현합니다.

**남길 것:** 실행 방법, 입력·출력 예시, 평가 지표, 기준선 결과와 한계.

**완료 기준:** 복잡한 방법이 실제로 개선해야 할 비교 기준이 있고, 결과를 재현할 수 있습니다.

## 6. 알고리즘·제품 흐름 선택 및 구현

**할 일:** 문제 유형에 맞는 후보를 [알고리즘 선택 가이드](algorithm-guide.md)에서 고릅니다. 데이터가 작고 시간이 짧다면 후보를 좁히고, 전체 서비스보다 핵심 사용자 흐름을 먼저 구현합니다.

**남길 것:** 선택 이유, 대안, 성공·실패 조건, 사람이 판단해야 하는 부분을 `docs/decisions.md`에 기록합니다.

**완료 기준:** 입력부터 사용자에게 보여줄 결과까지 한 흐름으로 동작하며, 핵심 결과를 설명할 수 있습니다.

## 7. 검증과 비교

**할 일:** 문제에 맞는 평가 방법으로 기준선과 새 방법을 비교합니다. 학습/검증 분리, 시간·그룹 누수, 편향, 엣지 케이스, 실패 사례를 확인합니다. 시제품이면 대표 입력과 오류 상태를 사람이 점검합니다.

**남길 것:** 실제 실행한 명령, 환경, 표본 수, 지표, 실패 사례, 남은 한계. 실행하지 않은 검증은 완료로 표시하지 않습니다.

**완료 기준:** 핵심 주장을 뒷받침하는 근거와 반례·한계를 발표에서 구분해 설명할 수 있습니다.

## 8. 재현성·공개 점검 및 제출

**할 일:** 처음 받은 사람이 안내에 따라 실행할 수 있는지, 의존성·환경·데이터가 명시됐는지 확인합니다. Docker는 팀 개발 환경의 차이가 실제 장애가 될 때 도입합니다.

**남길 것:** README의 설치·실행·데이터 출처·제한, AI 및 외부 자료 사용 기록, 의미 단위의 Git 커밋.

**완료 기준:** 제출 체크리스트를 마쳤고, 공개할 수 없는 데이터·개인정보·비밀키가 저장소와 이미지에 포함되지 않았습니다.

## 시간 부족 시 우선순위

1. 규정과 데이터 권한 확인
2. 작동하는 기준선과 작은 end-to-end 시제품
3. 핵심 지표 한두 개로 비교 검증
4. 실패 사례와 한계를 기록
5. 문서·시연·제출 정리
